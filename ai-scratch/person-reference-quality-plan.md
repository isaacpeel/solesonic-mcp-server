## 1. Today (read-only, `solesonic-mcp-server@izzy-bot`, 2026-10-14)

`person_reference_image.reference_workflow_json`: FLUX.1 Kontext-dev fp8 → Canopus FaceRealism LoRA 0.4 → KSampler dpmpp_2m / beta / 30 steps, FluxGuidance 2.0, one `LoadImage` (`__REFERENCE_IMAGE_1__`), latent from the encoded photo at ~1 MP, no face pass.
`workflow_json`: FLUX.1-schnell text-to-image, 1024x1024.

## 2. Why skin looks like a rash

| # | Cause | Fixed by |
|---|---|---|
| C1 | The whole frame is redrawn at ~1 MP: in half- or full-body shots a face gets ~150–250 px, and the VAE turns skin detail into coloured mottling | FaceDetailer pass (§3.3) |
| C2 | Canopus FaceRealism is a FLUX.1-dev LoRA used on Kontext: it adds pore/redness texture that comes out as noise, and pulls the face off-identity | Leaving Kontext; no skin LoRAs |
| C3 | FluxGuidance 2.0 (below Kontext's 2.5) gives noisy, under-resolved texture | Leaving Kontext |
| C4 | dpmpp_2m / beta over-sharpens high-frequency speckle | Qwen on euler / simple |
| C5 | fp8 UNet + fp8 T5 | bf16 everywhere (128 GB allows it) |
| C6 | Phone-photo sensor noise and JPEG blocks get copied | Reference pre-scale (§3.2) |
| C7 | Feeding outputs back in as inputs compounds artifacts | Description tells the model to edit from the original photo |

## 3. Target ComfyUI graph (Qwen-Image-Edit-2511, quality)

### 3.1 Models on the Spark (`ComfyUI/models/…`)

| Folder | File | Note |
|---|---|---|
| `diffusion_models/` | `qwen_image_edit_2511_bf16.safetensors` (~41 GB) | bf16, not fp8: memory is plentiful, and quantisation costs fine skin detail |
| `text_encoders/` | `qwen_2.5_vl_7b.safetensors` (bf16, ~16 GB) | Try bf16 first; fall back to `qwen_2.5_vl_7b_fp8_scaled` if load time hurts |
| `vae/` | `qwen_image_vae.safetensors` | |
| `ultralytics/bbox/` | `face_yolov8m.pt` | FaceDetailer detector |
| `sams/` | `sam_vit_b_01ec64.pth` | FaceDetailer mask |

Custom nodes: **ComfyUI-Impact-Pack** + **ComfyUI-Impact-Subpack** (FaceDetailer, UltralyticsDetectorProvider, SAMLoader). Nothing else; every Qwen node is core ComfyUI.

Spark specifics:
- aarch64: install `ultralytics` from pip into ComfyUI's venv and confirm the Subpack imports cleanly (check for a startup `IMPORT FAILED`).
- Unified memory is shared: Qwen bf16 + encoder + detailer is about 60 GB resident. If anything else runs on the Spark (e.g. the `qwen3-vl-30b-a3b` vision model the LLM API calls), check that the two fit together. The existing `/free` after `release-memory-delay-millis` (5 min) still applies.
- Expect seconds per image in the tens to low hundreds at 1 MP, 40 steps, cfg 4 (cfg > 1 doubles the work per step). The Spark's memory bandwidth (~273 GB/s) is its bottleneck. **Measure in Step 0.**

### 3.2 Graph (one per image count N = 1, 2, 3)

```
LoadImage ×N (__REFERENCE_IMAGE_1__ … __REFERENCE_IMAGE_N__)
  -> ImageScaleToTotalPixels (lanczos, 1.0 MP) ×N                       # C6: normalise size, soften JPEG noise
UNETLoader qwen_image_edit_2511_bf16 -> ModelSamplingAuraFlow (shift 3.0) -> CFGNorm (strength 1.0)
CLIPLoader qwen_2.5_vl_7b (type qwen_image) ; VAELoader qwen_image_vae
TextEncodeQwenImageEditPlus (clip, vae, image1..imageN, prompt = __PROMPT__)   -> positive
TextEncodeQwenImageEditPlus (clip, vae, image1..imageN, prompt = "")           -> negative
VAEEncode(scaled image1) -> KSampler.latent_image                            # output follows photo 1's aspect ratio
KSampler: seed __SEED__, steps 40, cfg 4.0, euler, simple, denoise 1.0
VAEDecode -> [3.3 FaceDetailer] -> SaveImage (filename_prefix person_reference_image)
```

Starting values are taken from the stock ComfyUI 2511 template, then tuned in Step 0: steps 30–50, cfg 3.5–4.5, shift 2.5–3.5. For N ≥ 2, Step 0 also compares the latent from image 1 against `EmptySD3LatentImage` at 1328x1024 / 1024x1328; group shots may want a wider canvas than photo 1.

### 3.3 FaceDetailer pass (fixes C1)

`UltralyticsDetectorProvider(face_yolov8m)` + `SAMLoader(vit_b)` → `FaceDetailer` on the decoded image:
- model / clip / vae: the same Qwen loaders as above (so no extra model memory).
- positive: `TextEncodeQwenImageEditPlus` with **no images**, prompt `"natural photographic skin, even skin tone, soft realistic texture, sharp eyes"`; negative: empty. At low denoise, identity comes from the pixels already there. Feeding the full reference photos into a face crop would confuse the model.
- `guide_size` 1024, `max_size` 1024, `denoise` 0.30 (tune 0.20–0.40), steps 20, cfg 3.0, euler / simple, `feather` 10, `bbox_crop_factor` 3.0, `noise_mask` on, `drop_size` 32, `bbox_threshold` 0.5.
- Every detected face is processed, so 2–3 people need nothing extra.

If Step 0 shows identity drifting in the detailer, lower `denoise` to 0.2 before changing anything else.

### 3.4 Text-only fallback (`workflow_json`)

It stays FLUX.1-schnell. The router only sends `person_reference_image` requests that have photos, so this path is effectively unused. A 2511 graph with no images would also work, but isn't worth the step count.

### 4.2 Schema: `V3__create_comfy_workflow_reference_variant.sql`

```sql
CREATE TABLE comfy_workflow_reference_variant (
    id                UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    comfy_workflow_id UUID        NOT NULL REFERENCES comfy_workflow (id) ON DELETE CASCADE,
    image_count       SMALLINT    NOT NULL CHECK (image_count BETWEEN 1 AND 3),
    workflow_json     TEXT        NOT NULL,
    created_at        TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at        TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    UNIQUE (comfy_workflow_id, image_count)
);

-- Carry every existing variant across, counted by its distinct __REFERENCE_IMAGE_n__ tokens.
INSERT INTO comfy_workflow_reference_variant (comfy_workflow_id, image_count, workflow_json)
SELECT id,
       (SELECT count(DISTINCT match[1]) FROM regexp_matches(reference_workflow_json, '__REFERENCE_IMAGE_(\d+)__', 'g') AS match),
       reference_workflow_json
FROM comfy_workflow
WHERE reference_workflow_json IS NOT NULL AND reference_workflow_json <> '';

ALTER TABLE comfy_workflow DROP COLUMN reference_workflow_json;
```

- Why a child table rather than a jsonb map: each variant is a full graph edited on its own, `UNIQUE` stops duplicate counts, and the check constraint mirrors `MAX_REFERENCE_IMAGES`.
- The column is dropped so there's one source of truth. Back it up before migrating (`SELECT tool_name, reference_workflow_json FROM comfy_workflow`).
- Ownership/grants: follow whatever V1 does with `${DB_OWNER}`.
- Tests run on H2 with Flyway off, so the migration is only exercised against Postgres (verified manually, §6).

## 5. Data: `scripts/comfy-workflow-person-reference-qwen.sql`

Run after V3 has been applied (i.e. after deploying the new build once).

1. **Source**: the Step 0 winner exported via Workflow → Export (API) for N = 1, 2, 3 (or one export for N = 3, with the 1- and 2-image graphs derived programmatically by removing `LoadImage` / scale nodes and the `image2` / `image3` inputs).
2. **Tokenise**: `__PROMPT__` (positive encoder only), `__SEED__` (main KSampler; the FaceDetailer seed stays fixed), `__REFERENCE_IMAGE_1..N__`, `filename_prefix` = `person_reference_image`.
3. **Validate** (script generator, before writing SQL): every edge resolves, tokens are contiguous 1..N, no test filenames or prompts are left over, and the detailer prompt isn't tokenised.
4. **SQL**, one transaction: `DELETE FROM comfy_workflow_reference_variant WHERE comfy_workflow_id = (person row)`, then insert three rows (`image_count` 1, 2, 3) dollar-quoted, then update `description`, then `COMMIT`. Re-runnable.
5. **Description** (what the chat model reads to pick the tool and write the prompt):

> Edits one, two or three photos of people while keeping each person recognisably themselves — face, skin tone, hair, facial hair, glasses and build are preserved — and changes what the user asks: setting, clothing, pose, lighting, framing, or combining people from separate photos into one shot. Use this whenever the user attaches photos of people and wants to see those people somewhere else, doing something else, or together.
>
> Write the prompt as an edit instruction. Refer to people by photo ("the man in image 1", "the woman in image 2"); do not re-describe their faces. State what changes, then what must stay the same. Example: "Place the man in image 1 and the woman in image 2 side by side on a beach at golden hour, both in white linen, him with an arm around her shoulders. 85 mm portrait, soft natural light, shallow depth of field. Keep both faces, skin tones, hairstyles and his glasses exactly as in their photos; natural, even skin texture." Avoid words like "ultra-detailed skin", "visible pores" or "gritty".
>
> Always edit from the user's original photos, not from a previous result. The output follows the first photo's aspect ratio and takes noticeably longer than plain text-to-image generation.

6. The existing Kontext update script `scripts/comfy-workflow-update-person-reference.sql` is deleted (it targets node ids that will no longer exist).

## Risks

- **Speed on the Spark** is the main unknown. If p95 is unacceptable, first drop to 30 steps, then try the fp8 text encoder. Lightning stays off (Q4).
- **Three people from three photos** is the hardest case for any model. Expect occasional identity swaps between people; the per-photo naming in the prompt is the main mitigation.
- **FaceDetailer on aarch64**: if `ultralytics` won't install, use the Impact Pack's `MediaPipe-FaceMesh` or `SAM`-only detection, or skip the detailer for close-ups.
- **Shared unified memory** with any LLM running on the same Spark.
